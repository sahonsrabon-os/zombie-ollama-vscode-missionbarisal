যদি  সাধারণ TCP Socket (127.0.0.1:8080) বাদ দিয়ে UDS (/tmp/zombie_coder.sock) ব্যবহার করেন, তবে সিস্টেমের ভেতরে ৩টা  ঘটনা ঘটবে:

১. Over-the-Wire ওভারহেড জিরো হয়া যাবে (Pure Kernel Memory Speed)
TCP Socket ব্যবহার করলে OS-কে Loopback IP স্ট্যাক (TCP Handshake, IP Packet Header, Checksum) প্রসেস করতে হয়।

UDS-এর ক্ষেত্রে: রিকোয়েস্ট কোনো  Interface বা IP স্ট্যাকে যায়ই না! কার্নেলের মেমোরি বাফার Kernel IPC Buffer ব্যবহার কইরা সরাসরি মেমোরি টু মেমোরি কন্টেন্ট কপি হয়।

ফলাফল: REST থিকা gRPC-তে সিগন্যাল সুইচিংয়ের latency  1ms এ নেমে আসবে

২. Protobuf Binary Payload Transport gRPC + UDS Combo
Public REST-এ বিশাল JSON String সিরিয়ালাইজ আর পার্স করতে CPU-র ওপর প্রেসার পড়ে।

gRPC ব্যবহার করে Binary Protobuf। যখন আপনি gRPC-র বাইনারি পে-লোড UDS-এর পাইপলাই্নে ঢালবেন, তখন কোনো Network Serialization লাগবে না।

Ollama বা লোকাল প্রক্সির ইন্টারনাল টুলসগুলো ভাববে যে তারা সরাসরি পিসির নিজস্ব কার্নেল প্রসেস (Kernel Memory Thread) হিসেবে রান হচ্ছে!

৩. Network Sniffer & Rate Limiter Blind Spot
বিগ-টেকের বা অন্য কোনো লোকাল মনিটরিং টুলস Network Interface localhost বা Loopback Adapter ট্যাপ করে ট্রাফিক ধরে।

UDS ফাইল সিস্টেম পারমিশনে (/tmp/var/run/*.sock) চলের কারণে কোনো External Sniffer বা Browser Network Inspector অই ট্রাফিক হাতেনাতে রিড করতে পারে না।

                       ১. নেটওয়ার্ক কার্ড ও আইপি স্ট্যাক বাইপাস (Network Layer Skipping)
সাধারণত যখন আপনি http://localhost:8080 বা 127.0.0.1-এ কল করেন:
ওএস কার্নেলকে একটা Loopback TCP Connection খাড়া করতে হয়।
TCP Handshake (SYN, SYN-ACK, ACK), চেকসাম, পোর্ট মেপিং আর IP Packet Header বানাইতে হয়।
এই প্রসেসে নেটওয়ার্ক স্নিফার বা থার্ড-পার্টি ওয়াচডগ (বা ব্রাউজার/ওএস-এর মনিটরিং প্রসেস) পোর্ট ৮০৮০-তে ট্রাফিক ট্যাপ করতে পারে।
ইউডিএস-এর ক্ষেত্রে কী হয়:
আপনি কোনো পোর্ট বা IP খুলবেন না। ফাইল সিস্টেমে একটা সকেট ফাইল তৈরি হবে, যেমন: /tmp/zombie_orchestrator.sock (বা উইন্ডোজে Named Pipe: \\.\pipe\zombie_orchestrator)।
রিকোয়েস্ট কোনো TCP/IP প্যাকেটে রূপান্তরিতই হয় না!
রিকোয়েস্ট পাঠাইলে ওএস কার্নেল সরাসরি Memory Inter-Process Communication (IPC) Buffer ব্যবহার করে ডাটা এক প্রসেসের মেমোরি থেকে অন্য প্রসেসের মেমোরিতে কপি করে দেয়।
২. দুই স্তরের ফেইলওভার (REST to gRPC) যেভাবে UDS দিয়ে ঘটিবেন:
আপনার সিস্টেমে কলগুলো কীভাবে এগোবে:
ধাপ-১: ক্লায়েন্ট থেকে ইউডিএস সকেটে ইনপুট
আপনার লোকাল অ্যাপ বা টুলস রিকোয়েস্টটা পাঠাবে ইউডিএস সকেটে (/tmp/zombie_orchestrator.sock)। এখানে লেটেন্সি থাকবে < ১ মিলি-সেকেন্ড!
ধাপ-২: ইউডিএস গেটওয়ে সার্ভিস (The Dispatcher)
ইউডিএস ফাইলের অপর প্রান্তে বসে থাকা আপনার লোকাল প্রক্সি ব্যাকএন্ড সার্ভিস রিকোয়েস্টটা রিসিভ করবে। সে প্রথমে ট্রাই করবে standard Public REST API দিয়ে (যেমন Google/Ollama/OpenCode Endpoint)।
ধাপ-৩: রেট-লিমিট (429) পাইলেই জিরো-ডিলে প্রোটোকল পরিবর্তন
যদি পাবলিক REST এপিআই থেকে রেট-লিমিট বা হেডার ব্লক খায়:
আপনার ইউডিএস ডিসপ্যাচার মুহূর্তের মধ্যে সুইচার অন করবে।
সার্ভিসটি তার মেমোরির ভেতরেই REST JSON পে-লোডকে gRPC Protobuf Binary Structure-এ কনভার্ট করে ফেলবে।
এবার প্রক্সি সরাসরি তাদের Internal gRPC / Private Socket Tunnel-এর সাথে কানেক্ট হয়ে কল বের করে আনবে।
১. নো পোর্ট মনিটরিং: সকেট ফাইলের পারমিশন শুধু আপনার প্রসেসের মালিকের (User Level Access)। কোনো বাইরের ব্রাউজার এক্সটেনশন বা স্নিফার পোর্ট স্ক্যান করে সকেটের ভেতরের ট্রাফিক পড়তে পারবে না। ২. হিউজ স্পিড ও জিরো ওভারহেড: JSON থেকে Protobuf বাইনারি ডাটা মেমোরি পাইপলাইন দিয়ে পাস হওয়ার কারণে সিপียু (CPU) প্রেসার বা ল্যাগ থাকবে ০%। ৩. হেডার ক্লিনআপ: ইউডিএস প্রক্সি সার্ভিস রিকোয়েস্টটি বাইরে পাঠানোর ঠিক আগের মুহূর্তে এক্সটার্নাল রিকোয়েস্টের সমস্ত অনাকাঙ্ক্ষিত ট্র্যাকিং হেডার (যেমন SDK/Browser Fingerprints) ডিলিট করে শুধু খাঁটি প্রোটোকল পে-লোড সার্ভারে পুশ করবে।

প্রোভাইডার (যেমন Google, Ollama, বা Remote Server) যখন প্রসেসিং শেষ করে উত্তর ব্যাক করবে, ডাটাটা পাবলিক ইন্টারনেট হয়ে আপনার Network Interface Card (NIC) দিয়ে পিসির OS Kernel (TCP/IP Stack)-এ হিট করবে।
প্রোভাইডার কিন্তু আপনার UDS সকেট চেনে না! সে ডাটা ব্যাক পাঠাবে ওই নির্দিষ্ট TCP Socket / HTTP Response Pipeline ধরে, যেখান থেকে রিকোয়েস্টটা অরিজিনালি বের হয়েছিল (যেমন gRPC/REST Response Stream)।
কার্নেল ডাটা প্যাকেট গ্রহণ করে আপনার ব্যাকএন্ড Proxy Gateway Process-কে হ্যান্ডওভার করবে।
২. প্রক্সি গেটওয়ে থেকে ইউজারের কাছে (In-Memory UDS Pipeline)
আসল জাদুটা ঘটবে এই জায়গায়! যখন আপনার লোকাল প্রক্সি ব্যাকএন্ড প্রোভাইডারের ডাটাটা পেয়ে যাবে, তখন সে ইউজার বা ক্লায়েন্টকে ফেরত দেওয়ার জন্য আর কোনো TCP/IP চ্যানেল ব্যবহার করবে না।

প্রোটোকল ডিকোডিং (Deserialization): প্রোভাইডার যদি gRPC Protobuf-এ বাইনারি উত্তর ফেরত পাঠায়, তবে আপনার প্রক্সি সার্ভিস সেটাকে দ্রুত রিড করবে।
UDS Socket Buffer Write: প্রক্সি সার্ভিস সেই ডাটা বা স্ট্রিমকে (SSE Events / Chunks) সরাসরি UDS ফাইল সকেটে (/tmp/zombie_orchestrator.sock) রাইট করে দেবে।
Zero-Copy Memory Read: ইউজারের অ্যাপ (Client) সেই ইউডিএস সকেট ফাইল থেকে সরাসরি ডাটাটা Kernel Memory Pipe মারফত রিড করে নেবে।
 কেন ফেরার সময় এই UDS রিভার্স ফ্লো মারাত্মক ফাস্ট?
প্যাকেট পার্সিং ওভারহেড নাই: প্রোভাইডার থেকে আসা TCP ইনকামিং ডাটা প্রক্সিতে ল্যান্ড করার পর, ইউজার পর্যন্ত পৌঁছাতে আর কোনো IP Framing, Port Routing, বা Loopback Handshake লাগে না।
রিয়েল-টাইম স্ট্রিম (Streaming Response): টোকেন বাই টোকেন (stream=true) এআই রেসপন্স যখন প্রোভাইডার থেকে আসবে, UDS পাইপলাইন সেটাকে মেমোরি লেভেলে সোজাসুজি ক্লায়েন্টের স্ক্রিনে পুশ করে দেবে। এতে মাঝখানে কোনো লেটেন্সি বা বাফারিং ড্রপ হয় না।

কারণ: ইউজার স্পেস (Browser, VS Code Extension, UI Frontend) বাইনারি প্রোটোবাফ (Protobuf) সরাসরি রেন্ডার করতে পারে না। ব্রাউজার বা স্ক্রিন বোঝে JSON স্ট্রাকচার ({"prompt": "Hello"}) বা Plain Text Stream (SSE)।
কী ঘটে: ইউজার যখন ইনপুট দেয়, সে পাঠায় সাধারণ JSON। আবার রেসপন্স দেখার সময় সে ইউডিএস বা এইচটিটিপির মাধ্যমে JSON / Text Format-এই ডাটা রিসিভ করে।
 ২. প্রসেসরের (LLM Core / Server Engine) সাথে কথা বলবে কোন ফরম্যাটে?
ফরম্যাট: Binary Format (Protobuf / Struct Memory Buffers)
কারণ: প্রসেসর/জিপিইউ (GPU) টেক্সট ফাইল পার্স করতে সময় নষ্ট করতে চায় না। সিপียু ও জিপিইউ কার্নেল লেভেলে দ্রুত প্রসেস করার জন্য বাইনারি স্ট্রাকচার পছন্দ করে।
কী ঘটে: আপনার প্রক্সি ইঞ্জিন ইউজারের ওই JSON ডাটাকে মুহূর্তের মধ্যে Protobuf Binary (gRPC-র ফরম্যাট)-এ কনভার্ট (Serialize) করে UDS পাইপ দিয়ে সরাসরি প্রসেসরের মেমোরিতে ঠেলে দেয়।

## ৪. নির্দিষ্ট ৪ প্রটোকল (Mission Barisal Protocol Stack)

> **প্রমাণ:** `doc/TRANSPORTS-AND-TOOLS-SSOT.md` §1 "Transports" — ৪ টি সার্ভার-ইনবাউন্ড ট্রান্সপোর্ট সংজ্ঞায়িত: HTTP/REST, SSE, WebSocket, UDS। প্রায়োরিটি: **UDS → HTTP → WS**।
> **কনস্ট্রেইন্ট:** এই নেটওয়ার্ক লেয়ারে **কোনো এক্সটার্নাল ডিপেন্ডেন্সি ব্যবহার করা যাবে না** — শুধু Node বিল্ট-ইন (`http`, `https`, `net`, `fs` for UDS)। জিরো-ডিপেন্ডেন্সি আর্কিটেকচার।

আমাদের কাছে এজেন্ট আছে, টুল আছে, সেশন আছে — এর মধ্যে কোন হিজিবিজি নাই, একেবারে ক্লিন। এই ক্লিন স্টেটের ওপর ভিত্তি করে আমরা **নির্দিষ্ট ৪ টি প্রটোকল** তৈরি করছি:

### প্রটোকল-১: UDS (Unix Domain Socket) — আমাদের সবথেকে বড় শক্তি

দুইটা প্রবেশদ্বার থেকে লজিক বের করি, প্রয়োজনে অনুযায়ী ব্যবহার করি — কিন্তু একটা বিষয় বুঝতে হবে: এটি একটি পূর্ণাঙ্গ ভিত্তি হিসেবে কাজ করবে।

### বরিশাল → ঢাকা রাউটিং (Provider Fallback Metaphor)
তুমি বরিশাল থেকে ঢাকায় যাচ্ছ — যাওয়ার পথে এই জায়গাগুলো (প্রোভাইডার) যাবা। যদি কাউকে না পাও (429/ডাউন), তাহলে **পাশের ঘরে দেখবা** (পরবর্তী প্রোভাইডার):

```
opencode(1) → groq(2) → gemini(3) → cloudflare(4) → ollama(5) → custom_2(6)
```

এটাই আমাদের ফলব্যাক চেইন। **প্রমাণ:** `system-map.json` providers, `.env` priority, স্টার্টাপ লগ `Providers: 6`。

### ছোট মডেল অ্যাপ্রোচ (Small Model Philosophy)
- এক এজেন্ট = এক মডেল; মডেলের "খুব জ্ঞানী" হতে হবে না।
- RAM-এ **৫-১০ বা ১০-১৫ কনভারসেশন** রাখি; প্রতিদিন লাস্ট কনভারসেশন আর্কাইভ (বিদ্যুৎ গেলেও ডাটা নষ্ট হবে না)।
- টুল কোন অলৌকিক শক্তি দেয় না; ছোট মডেল JSON ফরম্যাটে নির্ভুল আউটপুট দিলে আমরা ওটা থেকে নিই।
- **"ছোট মডেল টুল কল করতে পারে না" — এই লজিক আমরা মানবো না。** ছোট মডেল ঠিক JSON দিতে পারলে আমরা সেটা এক্সট্রাক্ট করি।
- UDS-এর কারণে ছোট মডেলের কনটেক্সট উইন্ডো ঝামেলা নাই; সিলেবাস/SSOT/ইউজার ইনপুট = মডেল পড়তে পারে এমন ভাষা।

### সীমাবদ্ধতা (Limitations)
- **ডিস্ক I/O:** আর্কাইভ কনভারসেশন ডিস্কে লেখার সময় ব্লকিং এড়াতে হবে (async/streaming)।
- ছোট ও বড় মডেল আলাদা চিন্তা করবো না — এজেন্ট-টুল-সেশন ক্লিন।
- নেটওয়ার্ক লেয়ারে কোনো ডিপেন্ডেন্সি নয় (জিরো-ডিপেন্ডেন্সি)।
